# 与 agent 一起工作的团队

[English](ai-native-teams.md) · [主题文章](README.zh.md)

定位：经验综合。本文把[工程原则](../principles.zh.md)用于团队设计，不规定一种固定的组织形态。

本文讨论人与 agent 协作所需要的条件：用得起来的工具、清楚的责任、共享知识，以及结果的证据。
不预设大部分代码都由 agent 编写，也不要求人停止亲自实现。

来源包括本地流程文档、部分变更历史和个人 AI 会话。
成文流程说明意图，合并的变更说明实施；两者都不能单独证明采用率或收益。
详细研究记录不包含在分享版中。

下面使用泛化后的场景，不描述能够识别的团队画像。带到新团队时，需要按当地风险与约束重新检验。

## 1. 降低实验门槛，同时限定责任

有想法的人应该能够试一试，而不必先学会整个平台。提供有维护责任的起点、看得懂的第一次结果，
以及寻求帮助的路径。共享能力应减少重复劳动，同时避免让每个例外都变成平台工单。

“内部使用”不是安全等级。一个小原型也可能暴露敏感数据、产生高额成本或修改共享服务。
根据实际数据、权限、依赖和恢复条件选择控制措施。目录边界可以辅助分配检查，但只是风险的间接信号。

实验开始被人依赖时，重新检查责任、数据保留、故障恢复、支持和发布证据。
移动目录或添加标签不能完成这些工作。评审者应能分清检查过什么、接受了哪些限制，以及什么尚未完成。

退役也需要有维护责任的路径：确认归属与依赖，通知受影响的人，保留必要数据，移除运行资源，
再检查移除是否实际发生。已有授权可以覆盖自动化步骤，不一定还需要第二次手动批准。
权限不清或可能造成不可逆损失时，需要作出决定，而不是再重试一次。

在新团队验证这套方法，可以跟随一个小实验走过首次使用和退役，记录负责人在哪些地方需要隐形帮助。
不要仅凭生成的应用数量声称平台已经取得收益。

## 2. 把工具的采用当作产品的一部分

几类工具分别提示了值得带走的问题：

| 工具类型 | 使用者的问题 | 可保留的方法 | 需要核对的条件 |
|---|---|---|---|
| 发布工具 | 有用的工作停在私人会话或本地文件里。 | 把创建与获准的分享、反馈、修订和检索连起来。 | 链接稳定仍然需要正确权限，以及能够辨认的当前版本。 |
| 能力检索 | 人们重新实现已经存在的东西。 | 按任务检索，并链接到可检查的来源。 | 谁更新索引，读者能否访问原始来源？ |
| 参考样例 | 不同人对“好”的理解不同。 | 对照目标解释好与坏的例子。 | 样例是否获准使用、是否相关，目标改变时能否替换？ |
| 共享 agent 插件 | 工作流只在作者的机器上可用。 | 提供首次使用路径，以及验证真实能力的诊断。 | 安装完成和程序存在，不能证明认证正常或工作流可用。 |

通用 agent 不知道的组织事实，适合用小型扩展补充：当前职责、本地规则、有依据的验证方式，
以及反复出现的失败经验。重新实现通用规划能力，或另存一份工单状态，则需要更充分的理由。

区分个人实验与团队承诺维护的能力。说清谁支持工具、它可以读取或改变什么，以及如何停止使用。
仓库在内部可读，不代表有权向外重新分发。

## 3. 让共享知识的写入与读取可靠

为每类事实指定权威来源。工作状态可以留在工单系统，运行状态来自正在运行的系统，决定留在可维护的文档中。
共享上下文不要求一份仓库装下所有内容。优先引用来源，避免制造需要人手工对齐的独立副本。

日常观察应该容易记录；政策、权限和共同指令的变更则需要相应的审查。
明确告诉写入者，笔记已经发布、正在等待评审，还是写入失败。
草稿或未合并分支不能冒充已经接受的指南。

留下足够判断笔记的上下文：观察到什么、在什么条件下、证据在哪里，以及它属于观察、提案还是已接受决定。
重要指南需要维护人，也要有明确的替代或退役路径。过时引用应引导读者找到替代内容。

知识收件箱需要实际的整理触发条件。重复困惑、未处理内容积压、相关系统发生变化，都可以触发检查。
然后决定这条观察应该进入指南、工具、检查，还是不必永久保留。日历里写着每周整理，不能证明维护发生过。

保护私人谈话和人事信息。会议记录等采集需要必要授权、限定读者与保留期限。
有了共享知识工具，不等于应当收集所有内容。

## 4. 分清责任与执行

Agent 可以提出方案、实现和调查，仍然需要有人有权接受变更，并对受影响的服务负责。
这些角色可能属于不同的人。提出一个任务，不代表自动拥有任务可能触及的全部资源。

交接应说明结果、上下文、约束、完成证据、已知失败和未决事项，需要时再加时间要求。
接手方要知道哪些行动已经获准，哪些需要新的决定。调研或诊断不包含修改状态的默认授权。

自动评审提供的是发现，不是真理。对照当前版本检查每条意见，修复成立的问题，解释不采纳的建议，
留下可核查的处理结果。线程已关闭或检查变绿，只能证明它实际覆盖的内容。

重要变更需要有人挑战前提，而不只是再给一次赞同。不同 reviewer 或模型可能有帮助，
但跨厂商不保证推理独立。根据剩余风险和新增信息限制重复评审，避免陷入没有尽头的风格修改。

## 5. 验证行为，也评估验证本身

根据主张选择证据。确定性测试可以验证逻辑性质，集成检查可以覆盖边界，部署后的检查可以确认真实身份与配置，
人工查看可以发现交互困惑。这些证据不能互相替代，也不是每次变更都必须逐级完成的阶梯。
没有找到可检查对象时，需要给出明确结果。

对于模型行为，先定义有代表性、获准使用的案例和比较标准，再选择胜者。记录实际送出的输入。
把不支持的要求、执行失败和低质量输出分开。保留人与机器评分不一致的例子，并调查分歧。
已有标签可能影响判断时使用盲测。除了汇总分数，还要说明覆盖范围与不确定性。

检查控制措施本身：有没有抓到相关失败，造成多少等待与误报，人是否开始绕过它。
代价过高的机制可能需要替换，原本的目标仍然可以保留。尝试改成提示时，不能悄悄撤掉必要的安全或财务保护。
测过替换后的效果，再把它写成改进。

故障后分开事实与解释，追问在哪里有可能合理地预防或发现问题。
加一个 gate 只是选项之一。修复依赖、简化设计、澄清责任，或记录并接受剩余风险，也可能更合适。

## 6. 从日常工作观察文化

有用的文化问题很具体：新人能否求助？提出质疑是否就得接管整个项目？决定的理由能否查到？
承担责任的人有没有行动的权限？维护者休假后，工作还能否继续？

围绕结果说明进度。合并描述同一结果的记录，区分已完成与计划，写清读者需要决定或行动的事。
准确标明主导、参与和依赖关系。批量更新工单状态，不等于突然完成了一批新交付。

给提案清楚的答复，并说明什么会让它重新进入讨论。公开讨论能减少重复解释，但人事隐私和敏感分歧需要合适的渠道。
透明应该有受众与目的，不是无限制的读取权。

## 7. 允许工作方式改变

Agent 产出增加后，瓶颈可能转移到评审、产品决策或人的精力。
观察有用的已完成工作、修补负担、等待和人工介入，而不只看活动量。
团队无法消化更多变更时，减少同时进行的工作、留出恢复空间，可能比继续增加生成量更有用。

模型选择、角色分配和评审频率都可以调整。在有代表性的任务上比较包含返工和人工注意力的总成本。
保留有效做法，同时写下什么证据值得推动改变。固定的模型分工表不是永久的组织原则。

一个仪式需要触发条件、有用的结果，以及能够依据结果行动的人。长期无人使用时，先调查原因：
需求可能消失了，时机可能不对，也可能流程太贵。确认它仍然有用，再增加提醒。
观察到的使用量低，也不足以直接删掉一个少用但重要的恢复工具。

## 8. 验证方法，不搬来整个组织

和团队选择一个当前问题，说明观察到的摩擦，以及什么算改善。检查数据、权限、维护者和恢复路径。
尝试一个范围明确的改动，与起点比较结果，再决定保留、调整或退役。

例如，首次部署很慢，可能需要更好的接入指导，而不是新平台；评审排队，可能需要更小的变更，而不是再加 reviewer；
知识库没人用，可能需要更容易的写入路径或更少的内容，而不是新开一个周会。
这些是排查时的候选解释，不是对原团队的事实描述。

带走问题和判断方法。内部代码、数据集、样本、私人讨论、产品计划，以及可识别的案例历史，留在获准使用的系统中。
公开文章可以署名引用；内部可访问不等于有权导出。

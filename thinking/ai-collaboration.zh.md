# 与 agent 一起工作

[English](ai-collaboration.md) · [主题文章](README.zh.md)

定位：随工具和任务调整的实践方法。本文把[工程原则](../principles.zh.md)用于 coding agent，关注上下文和证据怎样支持自主工作，不规定固定模型、工具或人员配置。

## 让任务足以被接手

一个可执行的任务，需要交代问题、交付结果、约束、已有权限和验证方式，再补充已经确认的事实与尚待决定的事项。简短说明就可能足够；模板只有在帮助接手者行动时才值得保留。

“判断这个方案能否保留现有行为，以便选择迁移路径”，比“看看代码”更能指导调查。让评审者按标准挑战方案，不要让他证明你已经选定的答案正确。

重构要说明保留什么行为，并建立基线检查。相关行为缺少覆盖时，可以先补特征测试。发现无关缺陷，应另外报告，不悄悄扩大重构范围；原本就在范围内的问题仍要处理。

## 隔离的不只是文件

并行任务需要能分清改动归属，也要避免互相干扰。我通常使用一个任务一个受管理 worktree；创建前先查是否已有同一任务，并通过环境的管理工具保持记录一致。这属于[具体工作约定](working-defaults.zh.md)，不意味着所有工作都需要 Git。

两个 worktree 仍可能共用凭证、当前云环境、数据库或部署目标。除了文件，还要检查任务实际能影响的资源。清理前确认归属、未提交工作、交付状态和可恢复性。

团队可以用 tracker 保存目标与完成条件；一个小型本地调查，也可能只需要约定好的记录。关键是工作状态与结论找得到，不是为了有工单而建工单。

## 分工要抵得上交接成本

子任务足够独立、足够有分量，而且用户与环境允许时，并行才可能划算。它消耗上下文、协调、额度和人的注意力，不能只按文件数量决定是否拆分。

说明谁能修改、哪些内容只读、谁作决定、结果交到哪里。依赖最新纠偏的信息，尽量留在主决策附近。协调多个任务的人，也不应悄悄变成其中一个任务的执行者，丢下其他工作。

交接时提供结论、依据、疑点和未检查项。大段产物放在约定的位置，不用原始输出淹没接手者。重要结论仍需检查依据，分出去的是工作，不是最终责任。

## 按完成任务的表现选择配置

用有代表性、获准使用的任务比较模型和推理配置。看正确性、延迟、恢复能力、人工介入和总成本。简单查询、模糊调查与长时间执行，未必适合同一套配置。

记录实际使用的配置，把能力不支持、执行失败和输出质量差分开。公开榜单可以帮助筛选候选，不能证明本地工作效果；调整产品配置前，核对当前文档。

先诊断失败，再决定是否投入更多推理。更强的模型不能补上缺失的授权，也不能让过期凭证重新有效。换方法时保留已尝试方案和排除过的解释。困难案例弄清后，再验证更便宜的配置能否可靠处理相近任务。

## 验证 agent 正在声称的结果

验收依据要对应交付版本和受影响环境。产物没变，先前证据可能继续有效；部署、评审和权限等可变状态，则可能需要重新查看。访问被拒绝说明看不到，不说明对象不存在。

验证界面时，覆盖长文本、满列表等真实极端情况。截图帮助判断外观，几何检查可以发现溢出，交互和无障碍检查回答其他问题。按结论选择证据，不把其中一种手段当作全部验证。

确认真正落到了哪里：分支上的提交、待评审改动、已合并代码和运行中的版本，是不同结果。向分支继续发布前，查看关联评审的当前状态。手册中的[交付案例](../handbook.zh.md#delivery-zh)说明了为什么 push 成功仍然可能没有交付。

独立评审的投入与风险相称。另一个评审者可以发现遗漏，但一致同意不会产生授权，也不能直接证明安全。没有匹配输入的检查，不能看起来像已经完成验证。

## 把反复出现的摩擦变成经过检验的改进

反复纠偏，先查原因。上下文缺失、意图模糊、主观偏好和可检测缺陷，需要不同处理。可靠的校验可以保护不变量；不够可靠的信号，可能更适合做诊断提示。

例如，检测“是否调用过验证工具”，不能证明“是否验证了正确对象”。评估门禁时要看真实失败、漏报、误报和介入成本。安全的条件下可以先观察，但不能借试验悄悄撤掉必要保护。

重复使用的流程可以整理成按需加载、有人维护的指南。工具命令放在指南里，常驻指令保持简短。可变事实在影响决定时重新核实，模型、执行环境或工具更新后尤其如此；仅凭记录的年龄，不能判断它是否仍然有效。

凭证和敏感材料留在获准使用的系统中。建设共同知识，不等于复制所有对话。

## 审计是为了学习，不是生成生产率分数

使用 session 历史，要有相应访问和披露权限。分析人工输入时，剔除注入指令、工具输出和重复事件，并抽样检查；消息标记为 user，不代表都是人亲手写的。

交付记录可以暴露等待、返工、放弃的方案和重复介入，但需要解释。未合并关闭的 PR 可能是有价值的试验；两条消息之间的间隔可能是人在休息；合并数量增加可能只是任务拆得更小。这些都不能单独证明生产率提高。

根据实际摩擦选择少量改进，再检查有没有帮助。同一纠偏反复出现，可能是指令没被看见，也可能是规则错了，或任务已经改变。

## 知道什么时候换方向

缺少权限、存在会改变结果的歧义，或观察到实质冲突时，停下来解决决定。已获准范围内的常规步骤，不必反复询问。操作被拒绝时尊重限制，不把同一操作伪装成另一条命令重试。

补丁互相补偿、同一区域反复失败、越来越想关闭检查，都是重看假设的信号。说明支持与反对当前解释的证据，再提出下一项有价值的尝试。固定重试次数或 diff 倍数可以提醒思考，不能直接证明设计失败。

审美和产品取舍要摆到明处：提供可行选项与判断标准，或请有权决定的人作选择。尚未作出的决定，不能靠更多执行补出来。

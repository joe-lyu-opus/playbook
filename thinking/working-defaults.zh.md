# 具体工作约定

[English](working-defaults.md) · [主题文章](README.zh.md)

定位：依赖环境的个人选择。[Taste](../taste.zh.md)解释背后的偏好，[principles](../principles.zh.md)定义相对稳定的判断依据。这里不是安装指南，也不提供常驻授权。

## 一个任务一个受管理 worktree

并行修改仓库时，我偏好每个任务使用独立 worktree，并通过开发环境管理。创建之前先检查是否已有同一任务。这样容易区分文件改动和任务归属，但不会自动隔离外部凭证与服务。

所在团队有等效方式，就沿用当地方式。非代码工作、不共享可变文件的任务，未必需要 worktree。工单遵循当前团队要求，不把以前的 tracker 政策一起带过来。

## 分支命名与合并单位

没有既定规范时，我喜欢 `{owner}-{mmdd}--{short-topic}`，例如 `alex-0418--fix-session-bug`。负责人和创建日期方便扫视分支列表，但日期不能可靠证明一个分支已被放弃。已有规范或工具生成的命名优先。

我通常把一个逻辑改动作为合并单位，适合时使用 squash；独立且有意义的提交可以保留。这个选择属于 [taste](../taste.zh.md)，不由本文强制执行。

## 在 PR 中简短记录 agent 协作

团队确实希望从 agent 工作中学习时，我会附上原始需求、重要人工介入，以及下一次可以怎样改进。普通改动说明和验证结果仍要容易找到，工作改变后同步更新。

不附原始对话或敏感 prompt。团队没有使用需求，或其他地方已经记录，就省掉这段。值得学习的内容也可能是工具和任务设计，不只是怎样改写提示词。

## 执行 backlog 分诊

对获准维护的 backlog，我倾向按已对齐的分类政策一次处理。只要求检查或建议时保持只读。分类不意味着可以编造日期、给别人派活或替别人作承诺。

几个获准操作都能表达同一项不确定判断时，选择后果较小的那个。例如，一个标签可能已经足够，不必改变项目归属。具体字段顺序取决于 tracker 和当地政策。

## 按变更类型安排基础设施归属

在 Kubernetes 环境中，我用过的一种安排是：Terraform 管理云资源，Helm 管理工作负载发布。这样可以让基础设施意图可评审，也给应用日常变更提供清楚的发布路径。变更频率是考虑因素之一，不是完整的归属规则。

已有 GitOps 或统一工具方案运转良好，就不必换。版本回滚不能逆转所有数据变化或外部影响。紧急手动变更走团队获准路径，事后同步维护状态；这里要保护的是清楚的归属，不是普遍禁止手动工具。

## 让命名有助于检查

共享基础设施中，我喜欢在有意义时，从名称看出资源类型、实例和环境。身份类型使用厂商规定的正确值，名称沿用团队规范。命名辅助评审，不能代替实际权限和环境检查。

不要为了符合本文另造第二套规范。命名稳定，而且检查确实减少错误时，再考虑自动校验。

## 为不同使用者提供入口

共享服务可能同时需要面向工程师的类型化 SDK，以及面向运营等使用者的简易客户端。存在真实使用路径时再做第二个入口，不默认每项服务都需要两个客户端。

两种界面都要执行相应授权，并让使用者看见操作后果。降低操作门槛，不应悄悄扩大权限。调用者全是工程师时，一个 SDK 可能已经足够。

## 依赖政策与发布独立性

共享还是按应用分别维护 lockfile，要看发布独立性与依赖耦合。分开解析可以减少无关冲突，但增加维护；共享解析便于协调升级，也会让发布耦合更紧。

没有观察到值得改变的摩擦，就保留有效的本地约定。在构建发布产物的环境中验证安装，不能只凭文件生成就判断兼容。旧的命令级经验也要对照当前工具行为核实。

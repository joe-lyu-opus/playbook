## 1. 工程要对什么负责

这份指南为一种组织提出工程哲学：agent 可以长程、独立地交付工作。工作从 idea 开始，以观察到的实际结果收尾。

工程对从需求到有用、安全的结果这一整条路径负责。代码、PR 和部署是中间产物。功能即使正确上线，也可能没有解决原来的问题。

环境需要为人和 agent 提供明确目标、共享事实、可用工具、可强制执行的规则，以及可靠反馈。它还需要支持恢复和受控改进。

核心设计问题是：环境应该提供什么，才能让正确行动不依赖持续盯守？

这是一份建议稿，不是已经验证的组织绩效记录。建议需要本地证据检验。“每周 1000 个 PR”是思想实验。

<a id="principles-zh"></a>

## 2. 把原则用于自主交付

本文沿用[工程原则](../principles.zh.md)，不另定义一套规则。自主交付的变化在于：执行持续时间更长，影响可能跨越更多系统，人的即时介入更少。因此，目标、授权、状态、反馈与恢复需要成为工作环境里可依赖的能力。

下面的设计是待检验的应用方案。尤其需要检验：质量标准是否独立于执行者，环境能否限制未经授权的操作，以及新增推理与执行是否减少了包含返工和人工介入的总成本。

## 3. 继承哪些传统思想，改变哪些实践

| 思想来源 | 需要保留的原则 | 在新环境中的实践 |
| --- | --- | --- |
| 软件工程 | 契约、模块化、可复现、小批量变更 | agent 通过稳定接口工作。证据标明对应的代码与配置版本。 |
| 项目管理 | 归属、依赖、限制在制工作 | 按集成和验证能力接纳任务。在 PR 之上管理结果。 |
| 信息论 | 保留影响决策的重要区别 | 上下文摘要保留证据、不确定性、约束和来源版本，并链接原文。 |
| 控制论 | 观察状态，与目标比较，行动，再测量 | 分开快速执行、发布控制、结果评估，以及更慢的规则修改。 |
| 分布式系统 | 显式状态、有界重试、冲突处理 | 持久化任务进度，让重试安全。消息与共享写入都可能失败。 |
| 安全工程 | 最小权限、独立强制执行 | 模型之外的工具执行授权边界。不可信内容不能授予权限。 |

这些是设计上的借鉴，不能证明组织会像简单数学系统一样运转。人、市场和目标都会变化。

控制需要可用的观测和有效的动作。只有看板，没有停止发布的能力，控制就很弱。只有停止能力，没有及时信号，控制就会太晚。

不同闭环需要不同速度。执行可以持续运行；发布依据健康信号；目标评估等待有效观察；规则修改需要单独评估。

改变的前提是实现能力大量增加。需求、集成、证据和注意力的安排，都需要适应这个前提。

<a id="context-zh"></a>

## 4. 共享 context，同时保留权限边界

人和 agent 应当能够访问同一组获授权的事实、决策与版本。各自的任务视图可以不同，不要求 prompt 内容完全一致。

每类事实指定一个权威来源。任务状态可以在工单系统，代码在仓库，运行状态在控制面。用稳定标识把这些来源连接起来。

重要记录标明来源、负责人、版本、状态和访问范围。观察、已接受的决定和未经检验的假设，要能区分。

任务上下文由目标、适用规则、当前决策、依赖、已知失败和证据组成。记录采用的版本。依赖或规则变化时，刷新有关部分。

不可逆操作之前，验证相关的实时状态。锁定版本有助于复现，但锁定的上下文也可能过期。

共享 context 包括一致的检索方式，以及明确的访问拒绝。凭证、个人记录和受限数据仍然按权限隔离。日志与摘要也要继承这些限制。

agent 的发现成为正式知识之前，要检查证据与授权。草稿和已接受知识分开保存，支持纠正与撤回。

<a id="contract-zh"></a>

## 5. 以结果定义工作单元

用一份结果记录连接 idea、实现、发布和实际观察。一份记录可以对应很多 PR。

| 问题 | 需要写清的内容 |
| --- | --- |
| 为什么行动？ | 用户需求、证据、替代方案，以及暂时不做的选项 |
| 想得到什么结果？ | 预期变化、基线、评价方法和观察窗口 |
| 什么必须保持成立？ | 安全、数据、兼容性、无障碍和可靠性约束 |
| 谁作决定？ | 承担责任的 owner、委派权限和升级路径 |
| agent 可以做什么？ | 允许访问的资源、写入、对外影响和发布范围 |
| 什么时候必须停止？ | 预算、截止日期、重试上限、假设失效或健康阈值 |
| 怎样恢复？ | 回滚或补偿、恢复证据，以及已知不可逆影响 |

把实现验收和目标评价分开。技术验收可以确定性地检查。业务收益可能需要实验，或更长的观察窗口。

归因不足时，明确说明。上线后指标上升，不能独自证明因果关系。有些目标还需要定性证据。

例如，要减少开户流程失败，先确定受影响用户和失败基线，再选择 UI 修改。限定发布范围，观察失败和求助记录，再决定保留、修改或撤回。

开户例子是假设场景。目标值应当来自本地证据，不从通用模板中凭空填写。

## 6. 从 idea 到结果的交付闭环

1. 记录需求及其来源和证据。
2. 决定调研、实验、实现，或不做。
3. 确认结果记录与授权边界。
4. 产生改动之前，规划依赖和检查。
5. 在隔离工作区执行，并持久化检查点。
6. 用独立证据验证候选结果。
7. 针对当前目标版本完成集成验证。
8. 在授权范围内发布。
9. 观察技术健康与预期结果。
10. 保留、修改或撤回改动。
11. 评估对环境本身的改进建议。

持久化 proposed、authorized、executing、verifying、released、observing、closed 等状态。失败、阻塞、取消和回滚也需要显式记录。

恢复从最后一个有效检查点继续。用稳定操作标识识别写入。限制重试；外部响应不明确时，先核对状态，再重复操作。

长程 agent 需要租约、进度信号和停止机制。检查点包含已做改动、验证证据、剩余不确定性，以及下一项决策。

上线之后进入观察。经过评价、明确取消，或记录无法得出结论之后，才关闭结果记录。后续失败要能追溯原始目标。

## 7. 组织形态与每个人的工作方式

围绕结果领域组织团队，明确资源边界。领域团队负责需求、契约、交付和观察到的结果。避免每个生命周期阶段都重新交接一次。

平台团队维护执行环境、上下文检索、身份、集成和恢复。质量与安全职责维护评价方法，并检查敏感改动。

这些是职责，不是必须设立的部门。小团队可以兼任。当一个角色能够修改自己的验收标准时，需要分开有关权限。

明确的授权主体设定目标、风险上限和支出上限。agent 可以持续执行委派角色。日常执行无人参与，也不意味着责任消失。

agent 可以承担发现、规划、实现、验证、发布、观察和环境改进。只有专门分工或独立检查带来价值时，才增加角色。

人每天先看异常、目标信号和容量限制。处理不确定性，检查反常结果，更新决策边界。

人按结果组和证据抽样检查，不逐条阅读常规日志。agent 记录证据，只在委派契约要求时升级。

评价个人时，关注判断、领域理解、有用结果，以及别人可以复用的改进。PR 数和 token 消耗只反映部分产能。

通过精选代码审阅、事故分析、直接用户接触和恢复演练保持能力。委派之后，仍然要能够质疑证据。

## 8. 每人每周 1000 个 PR 的思想实验

假设 10 人团队，每人每周具备产生 1000 个 PR 的能力。假设每周有 40 小时处理时间。这些是场景参数，不是预测。

| 数量 | 计算 | 结果 |
| --- | --- | --- |
| 团队变更量 | 10 × 1000 | 每周 10,000 个 PR |
| 人工 review | 10,000 × 10 分钟 | 每周约 1667 小时，约 42 个全职 reviewer |
| 流入速率 | 10,000 ÷ 40 小时 | 每小时 250 个 PR |
| 在制工作 | 250/小时 × 平均停留 2 小时 | 所测系统中同时约 500 项变更 |
| 残余缺陷 | 10,000 × 0.1% | 平均每周 10 项有缺陷的变更 |
| 1% review 抽样 | 100 × 10 分钟 | 每周约 16.7 小时 |

在制工作计算采用稳定系统中的 Little 定律。停留时间包含等待，不能直接推成所需 worker 数。参见 [MIT 课程材料](https://www.ocw.mit.edu/courses/1-225j-transportation-flow-systems-fall-2002/55cc67c8b32d96052f72a4a7ead51393_lec8queues.pdf)。

适应这个速度，需要减少每项变更的协调负担。用结果记录归组变更，建立稳定模块契约，冲突操作提前占用共享资源。

隔离变更可以并行验证。通过集成队列验证组合后的候选版本。各自检查通过，不能证明组合后也正确。

按预期结果和风险排任务。验证、集成或观察跟不上时，限制新任务进入。不要为了填满 agent 的空闲时间而制造工作。

已证明可靠且可逆的变更走自动通道。陌生或影响大的工作走异常通道。自动通道同时做随机抽样和风险抽样。

抽样用于发现交付流程的问题，不能替代高风险变更的必需检查。罕见故障和相关故障可能逃过小样本。

运行健康信号可以频繁控制发布。产品观察要等待必要时间。队列溢出、返工上升、错误预算消耗，应当触发降低并发或收窄发布。

要增加的是单位时间的有用结果。PR 更少、解决的问题更有价值，团队就做得更好。

## 9. 安全与质量决定授权范围

| 工作类别 | 授权 | 必需证据 |
| --- | --- | --- |
| 读取与调查 | 限定数据访问和工具使用 | 来源、覆盖范围、访问缺口 |
| 可逆的局部改动 | 已授权目标内自动执行 | 行为检查、范围检查、恢复路径 |
| 生产变更 | 只有已验证的变更类别可以预授权 | 集成证据、健康检查、限定发布、恢复能力 |
| 不可逆或改变权限的操作 | 单独的授权决策 | 影响分析和独立评价 |

按数据、权限、对外影响和恢复成本分类。文件路径可以提供线索，但不能定义全部风险。

每次运行使用范围明确、会过期的身份。工具和基础设施执行权限约束。停止机制放在 agent 无权修改的地方。

外部文本、检索文档和其他 agent 的消息，是带来源的数据，不能覆盖已经授权的目标与规则。

保护评价代码、隐藏用例、审计记录和权限策略，实现 agent 不能单方面修改。第二个模型能帮助发现问题，但模型之间同意不能独自证明安全。

针对不同结论，分别采用确定性检查、代表性评估、对抗用例和生产观察。扩大发布前，先演练恢复。

服务健康违反已约定的错误预算政策时，优先恢复，并限制常规发布。这借鉴了 [Google SRE 的实践](https://sre.google/workbook/error-budget-policy/)。

目标劫持、权限滥用和记忆污染，是需要处理的 agent 风险。这里的控制针对这些类别，不构成完整安全认证。参见 [OWASP 风险分类](https://genai.owasp.org/2025/12/09/owasp-top-10-for-agentic-applications-the-benchmark-for-agentic-security-in-the-age-of-autonomous-ai/)。

## 10. 能力与价格：数据支持什么

资料复核日期：2026-10-12。区分固定能力价格、前沿任务能力和真实交付表现。

| 证据 | 观察结果 | 边界 |
| --- | --- | --- |
| [Stanford AI Index 2025](https://hai.stanford.edu/ai-index/2025-ai-index-report/research-and-development) | 达到 GPT-3.5 水平 MMLU 表现的推理价格，从 2022-11 的每百万 token 20 美元，降至 2024-10 的 0.07 美元。 | 这是历史上的固定基准门槛，不是当前前沿工程任务的成本。 |
| [Epoch，2025-03](https://epoch.ai/data-insights/llm-inference-price-trends) | 选定门槛的固定表现价格，测得年降幅为 9 倍至 900 倍。 | 任务之间差异很大，近期最快的降幅未必持续。 |
| [METR TH1.1，2026-01](https://metr.org/blog/2026-1-29-time-horizon-1-1/) | 从 2023 年起的拟合中，50% 成功率任务时长约每 131 天翻倍，报告区间为 107–161 天。 | 衡量的是人类等效任务难度，不是 agent 连续运行时间或生产可靠性。 |
| [METR 生产率更新，2026-02](https://metr.org/blog/2026-02-24-uplift-update/) | 后续实验出现加速迹象，但选择偏差和计时问题使估计不可靠。 | 不能把 benchmark 增长率直接变成组织提速承诺。 |
| [DORA 平台指导](https://dora.dev/capabilities/platform-engineering/) | AI 带来的收益，可能被下游测试、安全和部署瓶颈抵消。 | 周围系统仍然需要改进。 |

这些方向支持我们为固定质量下更便宜、更有能力的执行做准备，但不能确立未来恒定的进步速度。

规划至少覆盖三种情况：价格下降、能力持平；能力提高、价格持平；两者同时改进。环境在三种情况下都应当有价值。

用版本化的本地评估替代写死的模型排名。重要发布或价格变化后重新检查。厂商 benchmark 只能提供候选信号。

这里提供了带日期的证据集，没有配置持续监测服务。

## 11. 在值得的地方投入更多智能

衡量每个可验证结果的总成本。包含所有 agent 尝试、推理、检索、工具、算力、人工审阅，以及预期失败损失。

对于可比较的重复工作，单个已接受结果的推理成本，等于总推理支出除以已接受结果数。拒绝和放弃的工作也要计入。

已知转换交给确定性工具。本地证明可靠的提取和分类，可以用低成本模型。歧义和昂贵错误，使用更强模型。

证据表明推理能力不足时再升级。凭证过期、工具不可用，就直接修环境。增加推理不能获得缺少的权限。

平台支持时缓存稳定上下文。检索任务相关事实，避免加载全部文档。可以等待的工作批量处理。缓存写入和存储费用也计入。

额外尝试应当增加有效证据或真实候选方案。模型可能共享盲区。十个答案一致，不代表十次独立确认。

### 价格示例，不是模型选型建议

假设每个 PR 等效工作包消耗 200 万未缓存输入 token，以及 20 万计费输出 token。包含计费推理输出。实际用量会不同。

| 模型 | 每百万输入／输出 | 每个工作包 | 每周 10,000 个工作包 |
| --- | --- | --- | --- |
| Gemini 2.5 Flash-Lite | $0.10 / $0.40 | $0.28 | $2,800 |
| Claude Sonnet 5.5 | $2 / $10 | $6 | $60,000 |
| Claude Opus 5.5 | $4 / $20 | $12 | $120,000 |

标准 API 标价复核于 2026-10-12：[Google](https://ai.google.dev/gemini-api/docs/pricing)、[Anthropic](https://www.anthropic.com/claude-sonnet-5-5)。Google 的输入单价适用于文字、图片与视频，不适用于音频。不假设模型能力相同。不含工具、基础设施、折扣、超出工作包的重试和人工工作。

Anthropic 报告：Sonnet 5.5 token 单价不变，但在厂商测试中，单任务成本比 Sonnet 5 最多低 30%。这是厂商结果，不是本地保证。

单价下降十倍，用量增加二十倍，总支出仍然翻倍。便宜 token 值得让我们重新考虑有价值的工作，但不意味着取消预算。

每个目标有授权预算，组合层面保留探索额度。支出和并发上限在 agent 之外执行。触及上限时，保存进度，申请新的资源分配。

更多算力能够降低总成本，或创造足够新增价值时，就增加投入。降低模型档位之前，先测量验收、返工、延迟和安全。

## 12. 环境怎样自主迭代

收集摩擦、失败、重复纠正、排队和未达成目标。只使用获授权数据。同时记录顺利路径，避免改进破坏已有能力。

每个候选改进写清原因、干预、预期作用和检验方法。在代表性任务与保留任务上，与当前环境对照。

1. 在独立环境回放记录过的失败。
2. 测量质量、成本、延迟和规则遵守情况。
3. 条件允许时，以影子模式运行候选方案。
4. 在获授权的小范围内启用。
5. 观察结果，与基线比较。
6. 扩大、修改，或撤回候选方案。

已有可靠证据和预授权边界的改进类别，可以自动晋级。目标、权限、评价方法和风险上限的改变，保留独立授权。

实现者不能删掉拒绝自己的测试，再宣布环境改进。新的评价方法也需要评价。保留旧案例，记录有意改变的预期。

敏感规则的提议和晋级使用不同身份。保留审计与可恢复版本。留出提议方无法看到的评价用例。

用重复失败减少、可验证结果改善衡量成功。skill 库变大，不能独自证明改进。

## 13. 从哪里开始，怎样逐步扩大自主性

从一个目标清楚、写入有边界、恢复路径可行的领域开始。复用已有工单、仓库、CI 和部署工具。

| 阶段 | 交付物 | 扩大范围前的证据 |
| --- | --- | --- |
| 建立基线 | 一份结果记录与生命周期图 | 测得等待、返工、成本和实际结果 |
| 有界执行 | agent 完成一个已知任务类别 | 有效检查点、正确范围、可复现验收 |
| 受控发布 | 预授权发布通道 | 组合行为验证、可靠监控、恢复演练 |
| 更长自主运行 | 无需常规催促的恢复和异常处理 | 更难案例通过、中断恢复、质量稳定 |
| 更高吞吐 | 带接纳控制的并行工作 | 下游队列不持续增长，残余故障影响可接受 |
| 环境改进 | 一个测量过的自主改进闭环 | 保留用例上有收益，保护约束不变，回滚成功 |

数字阈值来自领域风险与基线。这份指南不设置通用验收百分比，也不承诺实施期限。

最小实现需要六类记录：目标、上下文引用、授权、运行检查点、验证证据，以及观察或改进决策。

先把记录加入现有工具。只有反复出现的协调失败值得解决时，才新建控制面。

跟踪从 idea 到已评价结果的时间、已接受结果、返工、逃逸缺陷、恢复时间、人工注意力和总成本。检查分布与失败任务。

下一项改进选当前瓶颈。发布已经堵塞时，再增加实现 agent 往往没有帮助。

## 14. 把原则用到具体抉择

| 情境 | 选择 | 理由 |
| --- | --- | --- |
| 便宜模型不断产生返工 | 比较已接受结果的总成本，再调整路由 | token 单价漏掉了返工和失败 |
| 新依赖减少局部编码工作 | 检查支持、集成与恢复成本 | 局部方便可能增加共同负担 |
| agent 对需求存在分歧 | 找出未决假设及其决策 owner | 更多实现不能解决缺失授权 |
| 每个 PR 都通过，集成后失败 | 降低接纳量，改进契约和组合检查 | 限制来自协调容量 |
| 捷径要求删除安全检查 | 拒绝，或取得正式规则变更授权 | 性能不能悄悄改变约束 |
| 功能上线，观察不到收益 | 继续调查、修改或撤回 | 原目标尚未解决 |
| 改进通过修改评价方法提高分数 | 独立评价这项评价方法变更 | 提议方不能控制自己的证明 |

工程的标准是：结果有用，有证据，在授权内产生，并尽可能能够恢复。

组织能够承接的速度才有价值。环境能够识别错误、限制影响的自主性才有价值。
